# 系统架构

> 基于 [18 条设计原则](design-philosophy.md)——一个活的图谱，而非静态数据库。

## 核心抽象：活图谱（Living Graph）

### 为什么不用分层容器

早期设计将系统分为三个存储层：Stream（信息流）-> Atoms（原子记忆）-> Crystal（结晶洞察）。信息在容器之间单向流动，由独立的反思引擎处理。

这个设计有根本性问题：

1. **信息流不是线性的。** 在 Logseq 中写下的高度提炼的洞察已经是 Crystal 级别的内容——它不需要 Stream -> Atom -> Crystal 的管道。反过来，一条结晶（"我倾向于快速做决定"）可以触发一条新的原子记忆（"今天又快速做了个决定"）。层级是相互渗透的，不是单向管道。

2. **独立的反思引擎意味着系统的"活性"取决于引擎是否在运行。** 引擎空闲时，系统就是一个死数据库。根据原则 8（记忆通过使用而进化），进化应发生在检索的当下，而非下一个引擎调度周期。

3. **大脑没有"短期记忆盒"和"长期记忆盒"。** 它有一个连续的神经网络，不同区域具有不同的可塑性特征。记忆"层级"是巩固程度的连续谱，而非物理隔离的容器。

### 活图谱如何运作

系统的核心是**一张图谱**，每个节点拥有自己的"成熟度"。我们所说的"层级"不是预设的结构——它们是成熟度谱上涌现出的现象。

来自 Cursor 对话的一条新鲜信息碎片进入图谱时，是一个位于图谱边缘的小节点：连接少、成熟度低。随着它被使用、处理和链接，它自然"下沉"到密集的核心。高度连接的枢纽节点就是我们所说的"结晶"——但它们不是被"移动"到另一个容器；它们是在原地生长成那种形态的。

### Stream Log：图谱的外部事实锚点

Stream Log 存在于**图谱之外**，作为图谱的基底。

原因是：活图谱中的每个节点都至少经过了一步处理（被 LLM 拆分、分配类型、计算 embedding）。Stream 是未经处理的原始流——原始对话中的数千字、交错的代码、试错和闲聊。将所有这些原样插入图谱会严重污染信噪比（违反原则 9：耗散结构需要信噪比控制）。

但 Stream 不是无关紧要的审计日志。它扮演关键角色：

- **不可变的事实锚点。** 节点在多次再巩固后可能面目全非，但你随时可以回到 Stream 查看最初发生了什么。
- **AI 可访问的原始上下文。** 当 AI 需要更多细节时（"那次讨论的完整上下文是什么？"），它沿着节点的 `source` 指针读取 Stream——类似于再巩固过程中海马体被重新激活。
- **关系：** 每个节点都有一个指向其原始 Stream 片段的指针。Stream 和图谱不是两个独立的系统，而是同一事物在不同粒度上的表达——Stream 是无损的连续信号；图谱是有损的结构化蒸馏。

## 节点模型

### 四维成熟度

节点的状态由四个独立但相互作用的维度描述。这个设计灵感来自神经科学中记忆巩固所涉及的不同维度。

| 维度 | 描述 | 动态特性 | 神经学类比 |
|-----------|-------------|----------|----------------|
| **热度（Heat）** | 短期活跃度指标。最近创建、检索或使用的节点是热的。 | 快速衰减（每天，但衰减率受其他维度影响） | 近期神经元放电频率 |
| **精炼度（Refinement）** | 内容被处理的次数。原始 Stream 片段精炼度低；经 LLM 提炼后中等；多次再巩固后高。 | 缓慢增长，仅在再巩固时增加 | 记忆从模糊到清晰再到抽象的过程 |
| **连接度（Connectivity）** | 图谱中与其他节点的有效链接数量。不仅看数量——多样性很重要。全是 `tagged` 链接不如 `caused_by`、`analogous`、`contradicts` 混合有价值。 | 随链接创建/删除而变化 | 丰富连接的海马记忆更容易被回忆 |
| **独立性（Independence）** | 内容脱离原始上下文后的可理解和可使用程度。"2026-03-20 在 Cursor 中决定使用 SQLite"独立性低。"偏好个人工具的零运维方案"独立性高——自包含、可迁移。 | 通过再巩固逐步提高（具体 -> 抽象） | 从海马体依赖到皮层独立的迁移 |

**热度 vs. 成熟度：** 热度是短期的；其余三个是长期的。它们独立但相互作用：热节点更可能被选中进行再巩固（通过使用而进化），而再巩固提升成熟度。高成熟度节点即使变冷也不容易被归档（关键节点保护），而低成熟度冷节点最可能被遗忘。

**成熟度评分：** 四个维度分别存储（不同操作需要不同维度——`prepare` 优先考虑独立性，`explore` 优先考虑连接度）。对外排序使用加权复合分数，权重存储在可进化的策略库中。

### 节点类型

每个节点有一个 `type` 属性，影响其在图谱中的行为：

| 类型 | 描述 | 结构化程度 |
|------|-------------|-----------------|
| `fact` | 决策、结论、已确立的事实 | 高 |
| `context` | 项目信息、关系、当前状态 | 高 |
| `preference` | 编码风格、沟通偏好、工具配置 | 中 |
| `idea` | 灵感、假说、未验证的想法 | 低（链接更自由） |
| `crystal` | 从多个节点中涌现的高维认知产物——用户画像、行为模式、决策原则。不是单独的容器；是图谱中的枢纽节点。 | 最高 |
| `meta` | 系统运行记录——MCP 调用日志、策略变更、内部操作。默认在外部查询中隐藏；用于内部反思。权重极低。 | 内部 |

**`fact` 与 `idea` 的刚性差异**（呼应原则 10，混沌边缘）：`fact` 类型的链接创建需要更高的置信度阈值；`idea` 类型的链接可以更宽松（更低的 `strength` 阈值）。这确保了事实网络的可靠性与想法网络的灵活性共存。

### 派生分类（计算得出，非存储）

根据三个内容本质维度（`specificity`、`subjectivity`、`actuality`），在读取时计算出派生分类：

| 派生分类 | 含义 |
|-----------------|---------|
| `record` | 具体的、客观的、时间相关的 |
| `knowledge` | 通用的、客观的、持久的 |
| `belief` | 通用的、主观的、持久的 |
| `hypothesis` | 通用的、主观的、时间相关的 |
| `intention` | 具体的、主观的、面向未来的 |

### 链接模型

链接以丰富的元数据连接节点：

| 字段 | 类型 | 描述 |
|-------|------|-------------|
| `relation` | `LinkRelation[]` | `{type, confidence}` 对的数组。一条链接可以携带多种关系类型。 |
| `strength` | `number` (0--1) | 连接强度。通过 Hebbian 学习随时间衰减。 |
| `note` | `string?` | 可选的解释，说明这条链接为何存在。 |
| `auto` | `boolean` | 链接是否自动生成（vs. 人工确认）。 |
| `status` | `'confirmed' \| 'pending'` | 待定链接在被提升或丢弃之前等待评估。 |

**关系类型**（当前实现）：

| 关系 | 符号学类别 | 描述 |
|----------|---------------|-------------|
| `caused_by` | Indexical | 因果关系 |
| `continues` | Indexical | 时间延续 |
| `updates` | Indexical | 同一信息的较新版本 |
| `supports` | Iconic | 证据或支持论点 |
| `contradicts` | Iconic | 矛盾信息 |
| `summarizes` | Symbolic | 对源节点的高层摘要 |
| `part_of` | Symbolic | 更大概念的组成部分 |
| `analogous` | Iconic | 结构相似性 |
| `tagged` | Symbolic | 标签分类 |

### Crystal 节点与动态粒度

Crystal 节点没有固定大小。就像"狗"、"金毛犬"和"我的狗 Buddy"都是不同粒度层级的概念一样，Crystal 粒度由内容压力驱动：

**分裂：** 当内容超过阈值（如 500 字）且包含不同子主题时，Crystal 分裂为更聚焦的子节点，通过 `summarizes` 关系链接。

**合并：** 当几个小节点总是一起被检索、总是共同链接到其他节点、且相互 `strength` 很高时，生成一个新的父节点来综合它们（通过 `summarizes` 链接；原节点不删除）。

**无嵌套结构。** 嵌套会使图谱操作复杂化。通过链接关系（`summarizes`、`part_of`）表达层级更灵活——一个子节点可以同时属于多个父摘要。这更接近 Luhmann 的 Zettelkasten 方法：使用编号和引用来表达层级，同时保持每张卡片的原子性。

## 存储架构

### SQLite + FTS5 + sqlite-vec

所有数据存储在单个 SQLite 数据库文件中。这消除了部署复杂性，确保个人使用的零运维。

| 表 | 用途 |
|-------|---------|
| `nodes` | 所有记忆节点，含成熟度维度、结构角色标志和生命周期元数据 |
| `links` | 节点间的语义连接（关系以 JSON 数组存储） |
| `node_versions` | 再巩固节点的版本历史 |
| `operation_log` | MCP 调用记录（prepare/recall/digest） |
| `strategy_feedback` | Learning II 的策略评估数据 |
| `strategy_versions` | 策略文件版本历史 |
| `metadata` | 系统元数据（维护时间戳、schema 版本） |
| `agents` | Agent 身份表（多 agent 支持） |
| `note_sources` | 笔记集成实例（Logseq、Obsidian、Apple Notes） |
| `llm_usage_log` | LLM API 使用追踪 |
| `sync_hashes` | 源码到运行时的同步追踪 |

**全文搜索：** SQLite FTS5 提供 BM25 文本搜索，无外部依赖。

**向量搜索：** `sqlite-vec` 扩展在 SQLite 中直接存储 embedding 并执行近似最近邻搜索。图谱节点的 embedding 单独存储，通过节点 ID 关联。

**混合搜索：** 检索结合 BM25（词汇匹配）、向量相似度（语义匹配）、热度（时效性）和成熟度评分。权重可配置且可进化：

```
final_score = alpha * bm25 + beta * vector + gamma * heat + delta * maturity
```

### 冷启动门控

功能随数据积累渐进激活。门控系统检查节点和链接数量，避免在数据不足时运行高级功能：

| 功能 | 激活条件 |
|---------|---------------------|
| 基础 digest | 始终激活 |
| BM25 搜索 | 始终激活 |
| 向量搜索 | 节点 >= `vector_search` 门控值（默认：50） |
| 图谱扩展 | 链接 >= `graph_expansion_links` 门控值 |
| Crystal 生成 | 节点 >= `crystal_generation` 门控值 |
| 发散扫描 | 节点 >= `divergent_scan` 门控值 |
| Learning II | 节点 >= 500 且 recall 操作 >= 200 |
| Learning III | Learning II 运行 3 个月以上 |

## 认知接口

系统暴露三个 MCP 工具，映射到真实的认知操作而非数据库 CRUD：

| 工具 | 认知隐喻 | 何时使用 |
|------|-------------------|------|
| `brain_prepare` | "给我地图" | 每次新对话 |
| `brain_recall` | "按需检索" | 需要历史上下文时 |
| `brain_digest` | "消化这条信息" | 产生有价值内容之后 |

六个认知操作（digest、recall、prepare、explore、diverge、correct）被精炼为三个：

- **explore**（图谱遍历）和 **diverge**（发散搜索）是 `recall` 内部的检索策略，而非独立接口。外部 AI 不需要知道它在做向量搜索还是图谱遍历——它只需要相关信息。
- **correct** 是 `digest` 的特殊形式——"这个是错的"本身就是新信息，应该被完整消化（带审计跟踪和修正历史），而非简单的数据修改。

所有接口支持 **context 参数**——解释"为什么"要执行这个操作。Context 不仅提升当前操作的精度；它本身就是理解用户认知模式的有价值数据，为 Learning II 提供输入。

完整 API 参考见 [API Documentation](api.md)。
